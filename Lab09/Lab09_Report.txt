1. Inodes and Metadata

In my run of inode_inspector.py, dataset_sample.csv had Inode
Number 1442844 and a size of 46 bytes (the file content has spaces
after the commas in the header line). The permissions were
-rw-rw-rw- (0666).

If I rename the file with the mv command, the Inode Number does not
change. Linux keeps the file name separate from the file data and
metadata. The name is only an entry in the directory that points to
an inode. The inode stores the owner, size, permissions, timestamps,
and the location of the data blocks. mv only changes the directory
entry, so the same inode is used. (I can check this with ls -i
before and after mv.)

2. POSIX Permissions

Owner = Read/Write/Execute = 4+2+1 = 7
Group = Read/Execute = 4+1 = 5
Others = no access = 0

So the octal number is 750, and I would use os.chmod(file, 0o750).

3. The AI Context

In my run of os_security.py, after os.chmod(secure_file, 0o400) the
permission became -r--------, and the script's attempt to write to
the file failed with PermissionError: [Errno 13] Permission denied.
ai_weight_protection.py gave the same result with 0o444 and the
model file stayed safe.

OS permissions are safer than application logic because the Linux
kernel checks them every time any program opens the file, no matter
which program, script, or user tries it. A try-except block only
exists inside one program: it can be forgotten, written wrongly, or
missing in another person's script, and it does not stop a buggy
training job from opening the file in write mode. With 0o444, the
kernel refuses the write before any data is changed. One limit is
that a root user can bypass these permissions, so the cluster also
needs correct ownership (chown) and admin control.
