1. The Role of the Operating System

- File System & Permissions (Lab 9):
  In _execute_job(), the check "if not os.path.exists(dataset_path)"
  simulates the file system check. Workload_D_Hacker asked for
  secret_keys.txt, which does not exist, so it failed immediately
  with "FAILED: Dataset 'secret_keys.txt' not found or Permission
  Denied", before it got any RAM or GPU. (Note: os.path.exists only
  checks that the file exists, it does not check permissions, so
  this is a simple simulation of the check.)

- Memory Management (Labs 5/6):
  The "while True" loop with ram_lock checks available_ram_gb. A job
  is allowed to continue only if enough RAM is free, then the RAM is
  subtracted. If not, the job sleeps 0.5 seconds and checks again.
  Because the total allocated RAM never goes over 64 GB, the system
  never needs to swap to disk, so it avoids thrashing. In my output,
  the dashboard showed 8/64 GB free after A (40) and B (16) started,
  and 6/64 GB after C (2) started. (This is admission control by
  waiting, not real virtual memory.)

- Concurrency & Deadlocks (Labs 3/4):
  The line "sorted_gpus = sorted(req_gpus)" makes every job request
  GPUs in the same ascending order. Workload A asked for [2, 1, 0]
  but my output shows it waited for GPUs [0, 1, 2]. Since all jobs
  lock GPUs in the same order, a circular wait (one job holding GPU
  2 and waiting for GPU 0 while another holds GPU 0 and waits for
  GPU 2) cannot happen, so deadlock is avoided.

2. Hardware Utilization

In my live dashboard, Workload A used 40 GB RAM and locked GPUs 0,
1, 2. Workload B needed 16 GB RAM and no GPU, so it ran on the CPU
at the same time. After they started, the dashboard showed RAM
8/64 GB, GPUs 0-2 BUSY, GPU 3 IDLE, and Active Jobs: 2. Then
Workload C needed 2 GB RAM and GPU 3, and the dashboard showed
RAM 6/64 GB, all 4 GPUs BUSY, and Active Jobs: 3.

They did not block each other because their resource needs did not
conflict: the total RAM (40 + 16 + 2 = 58 GB) is under 64 GB, and
they used different GPUs (A: 0,1,2; C: 3; B: none). Each job runs
in its own thread, and a job waits only if the resource it needs is
taken. Workload C finished first (3 s), then B (6 s), then A (8 s),
and each one released its RAM and GPUs, ending at 64/64 GB and all
GPUs IDLE.

3. Course Reflection (AI Engineering Context)

A programmer who only writes basic Python/PyTorch scripts may not
know why a job becomes very slow or crashes. Understanding operating
systems helps me find the real cause. If training suddenly becomes
many times slower, I can check whether RAM is full and the system is
swapping (thrashing, as in Lab 6), and fix it by lowering the batch
size. If the GPU is idle, I can check whether the data pipeline is
I/O bound and pack the dataset into a sequential format (Lab 8).
For a shared GPU cluster, I can design job queues that check RAM
before running and request GPUs in a fixed order to avoid deadlock
(Lab 10). I can also protect production model weights with file
permissions (Lab 9) instead of trusting only application code. With
this knowledge I can debug and optimize systems like Kubernetes or
Slurm, not only run scripts.
